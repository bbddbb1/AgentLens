## Context

The active runtime path is span-driven, despite several documents and protocol comments describing an already-implemented immutable `EventEnvelope` ledger. `apps/api-ts/src/db/postgres.ts` explicitly drops the legacy `mission_events`, `graph_snapshots`, and checkpoint tables, then stores OTLP spans (including their span-event JSON), interrupts, ingest batches, and replay-branch/control records. `MissionStore.getReplayFromTelemetry()` reads those durable records and calls the pure `projectReplay()`/`projectTraceSnapshot()` functions in `apps/api-ts/src/services/runtime/projection.ts`; those functions synthesize `EventEnvelope`-shaped replay events, graph snapshots, and current runtime state on demand. Runtime summary and explanation are further deterministic projections over that replay, with runtime explanation already carrying `runtime_explanation.v1`.

Both `/api/v1/ingest/otlp` and `/v1/traces` await `MissionStore.ingestSpans()` and return HTTP `202` after its transaction commits. The Python `AgentLensOtlpJsonExporter`, however, recognizes only HTTP `200` as success. After ingest, the routes publish summary/explanation updates but no event whose contract means that durable evidence changed. The Web client instead includes `graph.snapshot.created` in its replay-reload list even though ingest creates no durable graph snapshot. Finally, `getAuditEvents()` and `verifyMissionIntegrity()` unconditionally report valid hash-chain integrity while the active tables do not persist or verify `content_hash`/`previous_hash`; the Audit UI amplifies this as cryptographically proven and secure.

This is a cross-cutting compatibility baseline spanning the TypeScript API/protocol/Web client, the Python exporter, tests, and directly contradictory documentation. It must preserve the durable span/control-record model and deterministic server-side projections rather than introduce the later runtime-adapter architecture.

## Goals / Non-Goals

**Goals:**

- Make the implemented durable-evidence and derived-projection boundary explicit in code contracts and directly affected documentation.
- Characterize externally meaningful span-to-replay/graph behavior before later projection implementations are introduced.
- Align OTLP client success handling with standard HTTP `2xx` semantics without changing valid server `202` responses.
- Make one best-effort publication attempt for the canonical `replay.updated` signal after evidence-changing ingest commits, and make the Web client reload replay when it receives that signal.
- Identify the active span-based replay/graph projection with a minimal stable version.
- Report integrity as unsupported/not verified until persisted hashes and verification exist.

**Non-Goals:**

- `RuntimeEvidence`, `TelemetryProfile`, capability/coverage models, adapter conformance, or any new framework adapter.
- Durable `EventEnvelope` storage, event sourcing/CQRS, graph-snapshot persistence, checkpoint normalization, or execution replay.
- Hash chains, signing, verification implementation, a schema registry, or a migration framework.
- New databases, queues, logs/metrics ingest, plugin loading, or broad UI/refactoring work.
- Using timing overlap, naming heuristics, or LLM output as authoritative runtime meaning.

## Decisions

### 1. Treat persisted telemetry/control rows as evidence and `projectReplay()` output as disposable projection

The baseline documentation and tests will identify `spans.events` as part of each persisted span row and `interrupts`/`mission_replay_branches` as explicit durable control evidence. `EventEnvelope` remains a useful shared protocol shape for projected replay events, not a claim that an envelope ledger exists. Graph snapshots, replay timeline events, current runtime state, summaries, and explanations remain generated by the server.

Only documents or comments that affirmatively contradict this implementation will be corrected, notably `docs/explanation/architecture.md`, `docs/explanation/background.md`, `docs/reference/agent-api.md`, `docs/reference/rops.md`, and ledger-oriented comments in `packages/protocol/src/types.ts`. Aspirational roadmap statements will remain clearly labeled as future work rather than being rewritten wholesale.

Alternative considered: restore `mission_events`/`graph_snapshots` and make the existing documentation true. Rejected because it redesigns persistence and violates the requested baseline scope.

### 2. Characterize public projection behavior at pure and route/service boundaries

Focused fixtures in `apps/api-ts/tests/unit/projection.test.ts` will exercise `projectReplay()` and `projectTraceSnapshot()` using OTLP-shaped spans and span events. Assertions will cover node lifecycle/status, parent-child dependency, tool success/failure, explicit interrupt projection, supported handoff/delegation, and absence of edges when an explicit relationship target cannot be resolved to a projected node. Explicit error/failed evidence must dominate completion defaults.

Tests will assert returned replay events, nodes, edges, statuses, evidence identifiers, and version fields rather than private helpers. Existing explanation tests remain useful but do not replace tests at the initial span-to-projection boundary.

Alternative considered: snapshot entire response blobs. Rejected because broad snapshots make intended semantics hard to review and couple tests to layout/order noise.

### 3. Keep server `202`; classify every `200 <= status < 300` as exporter success

The Python exporter will use the HTTP status class rather than equality with `200`. Tests will explicitly cover `200`, `202`, representative `4xx` and `5xx`, and request exception/timeout behavior. The existing empty-export and sandbox-mode behavior remains unchanged. API route tests will lock the two successful ingest routes to their current `202` contracts.

Alternative considered: change the server routes to return `200`. Rejected because `202` is already a valid success contract and changing it would hide the client defect.

### 4. Attempt one best-effort `replay.updated` publication after an evidence-changing ingest transaction commits

The current ingest contract is single-scope. `OtlpIngestRequestSchema` provides one optional `mission_id` and `branch_id` for the entire request; `normalizeOtlpJson()` flattens OTLP resource/scope spans into one span batch and one merged resource-attribute map; and `MissionStore.ingestSpans()` resolves exactly one `missionId`/`branchId` pair before writing every span in the request. This change preserves that constraint and therefore attempts at most one branch-scoped `replay.updated` publication per ingest request.

`MissionStore.ingestSpans()` will return the resolved `mission_id` and `branch_id` plus the outcome needed to reuse the existing duplicate-`batch_id` no-op path. The existing `ingest_batches` uniqueness check already commits and returns before span writes when `(mission_id, batch_id)` was accepted previously. This outcome may suppress `replay.updated`; the change will not add content comparison, generalized idempotency keys, or another no-op mechanism solely for notification decisions. All other successfully committed ingest paths are treated as evidence-changing under the existing upsert behavior.

After an evidence-changing commit, each ingest route will make one best-effort `publishMissionEvent(resolvedMissionId, 'replay.updated', { branch_id: resolvedBranchId })` attempt. The API does not guarantee exactly-once publication or delivery. A realtime transport failure will be contained so it cannot turn already-committed ingest into an HTTP failure. Validation failures, transaction failures, and the existing duplicate-batch no-op path will make no publication attempt. Existing asynchronous `runtime.summary.updated`, `runtime.explanation.updated`, interrupt, and sandbox events remain separate because they describe different updates.

The shared protocol will define the `replay.updated` message shape, including `type`, `mission_id`, and `branch_id`. The existing realtime manager remains the best-effort WebSocket/Redis transport. When the mission page receives the shared message, it will replace the unused `graph.snapshot.created` ingest-refresh assumption with `replay.updated` and reload only the matching branch. Route tests will assert one publication attempt after an evidence-changing commit and none after validation, persistence, or existing duplicate-batch no-op outcomes; Web tests will exercise handling of a delivered message rather than claiming delivery guarantees.

Alternative considered: publish `graph.snapshot.created`. Rejected because snapshots are computed on demand and no snapshot is created or persisted during ingest. Alternative considered: reuse summary/explanation updates. Rejected because those projections can fail or arrive independently and do not precisely mean that durable evidence changed.

### 5. Version the active span replay/graph projection as `span_projection.v1`

A shared `SpanProjectionVersion` constant/type will identify the algorithm. `ReplayStateResponse` and the top-level current-graph and graph-snapshots responses will expose additive `projection_version: 'span_projection.v1'`. Individual snapshots do not need their own registry or migration metadata because they are already nested in a versioned response. Existing `runtime_explanation.v1` remains unchanged and distinct.

Alternative considered: reuse `runtime_explanation.v1`. Rejected because explanation is downstream of replay/graph and can evolve independently. Alternative considered: introduce a general schema registry. Rejected as unnecessary for a one-version comparison boundary.

### 6. Model integrity as explicitly unsupported, not false-valid or compromised

Shared audit types will add a verification status and widen validity to a tri-state representation. Until verification exists, audit-event and verify responses will use `verification_status: 'unsupported'`, `is_valid: null`, and a not-verified hash-chain status/reason; branch reports will follow the same rule. `null` distinguishes "not evaluated" from both verified-valid and verified-invalid. Empty missions receive the same unsupported state rather than vacuous validity.

The Web Audit surface and its fallback state will render a neutral "NOT VERIFIED / unsupported" message and will not say "secure," "compromised," "verifying," or "cryptographically proven" unless a future implementation actually returns a verified result.

Alternative considered: return `is_valid: false`. Rejected because that incorrectly asserts detected corruption. Alternative considered: remove integrity endpoints. Rejected because an explicit unsupported response is more compatible and informative.

## Risks / Trade-offs

- **[Integrity response type widens from boolean to boolean-or-null]** -> Update shared protocol, API tests, audit store fallbacks, and UI rendering together; retain existing field names and add an explicit status/reason.
- **[Existing consumers may assume every replay response lacks a version]** -> Add the field without removing or renaming existing response fields and cover API/Web type checks.
- **[The post-commit publication attempt or delivery can fail or duplicate downstream]** -> Do not claim exactly-once delivery; contain publication errors so committed ingest remains successful, test the one-attempt route boundary, and rely on normal page reload/manual refresh as recovery.
- **[A characterization test could freeze an accidental heuristic]** -> Assert only requirements backed by explicit span status, parent IDs, relationship attributes/events, interrupt rows, and stable public output.
- **[Current relationship resolver can leave dangling targets]** -> Characterization acceptance requires both endpoints to resolve to projected nodes; implementation may tighten resolution but must not invent a target.
- **[Documentation has extensive aspirational ledger language]** -> Edit only direct present-tense implementation claims and clearly separate future architecture from the current baseline.

## Migration Plan

1. Add/adjust shared projection, realtime, and integrity types with additive projection/realtime fields and explicit unsupported integrity values.
2. Lock span projection and API route behavior with characterization tests, then make the minimum projection corrections those tests expose.
3. Correct exporter status classification and Python tests.
4. Emit and consume `replay.updated`, retaining interrupt and sandbox reload behavior.
5. Update integrity responses and the Audit UI together.
6. Correct contradictory documentation and run affected TypeScript, Web, and Python test/type-check suites.

Rollback can remove the additive projection/realtime fields and Web handler independently. Integrity rollback must not restore unconditional validity; if compatibility trouble arises, retain the explicit unsupported status while adapting the legacy fields at the edge.

## Open Questions

No blocking architectural questions remain. Exact helper/type names may follow existing package conventions, but the wire values `replay.updated`, `span_projection.v1`, and the unsupported/not-verified integrity meaning are fixed by this design.
